For any Claude session picking this project up next. Read this before touching any of the game's files.

## What this is

An HTML5/Three.js (r160) browser game built for Russ to run at "Outer Space Week" at RUN.world. Originally built single-file/base64-everything; as of Feature History #25 it's a real ES-module multi-file project instead (Russ's explicit call, once he confirmed the deployment is always served over http(s), never opened as a local `file://`). No build step, no bundler, no npm dependency at runtime — just files loaded directly by the browser via native `<script type="module">`/`import`. The two main-menu logo images are still embedded inline as base64 in `RuskosVoid.html`; every 3D model, however, is now a real external `.glb` file loaded via a real `THREE.GLTFLoader` — the player ship (#37), the five Void Rift orbiter drones (#39), and as of #40 the regular roaming turrets too. The hand-rolled base64/custom-parser GLB pipeline that used to handle the turrets and orbiters was removed entirely in #40, and as of #41 the void heart is a real loaded model too — every 3D model in the game now loads via `GLTFLoader` from an external `.glb`, nothing is base64-embedded or procedurally generated anymore. The game depends on real external assets: `RUSKOINTRO.mp4`, the `audio/` sample files (see #33/#34), `assets/player_ship.glb` (#37), `assets/enemy_drone.glb` (#39), `assets/turret.glb` (#40), and `assets/void_heart.glb` (#41).

## File structure

- **`RuskosVoid.html`** — markup + `<head>` only. Loads `style.css` via `<link>` and `js/game.js` via a single `<script type="module" src="js/game.js">`. No inline CSS or JS left in this file at all as of #25.
- **`style.css`** — all styling, unchanged content from before the split, just lifted out of the old inline `<style>` block verbatim (plus #27's new `.shopCard`/`.shopCardHead`/`.pip`/`.shopBuyBtn` rules replacing the old `.shopItem`/`.info`/`.lvl`/`.cost` rules).
- **`js/three.module.js`** — Three.js r160's actual ES module build (`three.module.min.js` from the official `three@0.160.0` npm package, renamed). This is what `game.js` imports. If Three.js ever needs a version bump, this is the one file to replace wholesale — re-fetch the matching `three.module.min.js` for the target version and swap it in; don't hand-patch it.
- **`js/GLTFLoader.js`** (new, #37) — the real `THREE.GLTFLoader` from the same `three@0.160.0` package, re-pathed with two `sed` edits (`from 'three'` → `from './three.module.js'`, `from '../utils/BufferGeometryUtils.js'` → `from './BufferGeometryUtils.js'`) so it resolves against this project's flat `js/` folder instead of an npm package layout. Used only by `buildShip()`'s player-ship loading — every other model in the game still goes through the original hand-rolled `parseGLB()` pipeline.
- **`js/BufferGeometryUtils.js`** (new, #37) — deliberately NOT the full upstream file. `GLTFLoader.js` imports exactly one function from it (`toTrianglesDrawMode`, only used for the rare TRIANGLE_STRIP/TRIANGLE_FAN primitive modes — none of this project's models use them, so it never actually runs, but `GLTFLoader` imports it unconditionally at module load time regardless). Vendoring the real ~1400-line utils file for one function would have pulled in its own extra dependencies (`computeMikkTSpaceTangents` and others) for nothing this project uses, so this file keeps only that function and the three constants it needs — same minimal-vendoring philosophy the project already used for the hand-rolled GLB parser.
- **`assets/player_ship.glb`** (new, #37) — the player ship's textured model, supplied by Russ via Tripo AI and optimized (mesh-simplified + textures resized) in a prior session. Loaded externally via `GLTFLoader`, not base64-embedded.
- **`js/game.js`** — the entire game (~449KB). Starts with `import * as THREE from './three.module.js';` and (as of #37) `import { GLTFLoader } from './GLTFLoader.js';` at true top-level (required — `import` can only appear as a top-level module statement, not inside a function), then the rest of the file is the same `(function(){ 'use strict'; ... })()` IIFE structure as before, kept as-is to minimize the diff during the migration (ES modules are automatically strict-mode and their own scope, so the IIFE is now technically redundant, but harmless to leave and safer than touching it unnecessarily). Section comments inside mark CONFIG · AUDIO · INPUT · SCENE · ENTITIES · EVENTS · UI · SAVE · LOOP.

## Working conventions established this project (keep using these)

**A real HTTP server is now available for end-to-end verification — a significant upgrade from every prior session's testing story, use it.** Since the game only runs over http(s) now anyway, spin one up in the sandbox (`python3 -m http.server <port>` from the directory holding all four files) and drive the *actual live game* with Playwright/headless Chromium, not just isolated CSS snippets. This was used for the #25 migration itself: loaded the real page, confirmed the deprecation warning is gone and zero console/page errors, clicked LAUNCH, let the intro fail over (no real video file in the sandbox) and the countdown run, screenshotted actual mid-flight gameplay (ship, HUD, asteroids all rendering correctly), then re-ran with `?debug`, pressed Backquote to jump into a live Void Rift, and screenshotted that too (heart HP bar, popup banners, orbiters all present and correctly laid out). This is real confirmation that the whole pipeline works, not just that the syntax is valid — **prefer this over the older isolated-snippet-screenshot approach whenever the change touches anything that only exists once the real game is running** (HUD wiring, event triggers, debug hooks, menu flows). The one thing it still can't judge is whether 3D-scene *motion/feel* (does a drone's dive look natural, is an explosion "impressive") is right — that's still Russ's call from an actual play session, screenshots only catch a single frame.

**For UI-only changes that don't touch the 3D scene at all (e.g. #27's Shipyard restyle), the live-server Playwright pass is still the right tool, just aimed at the menu overlay instead of gameplay** — go straight to the relevant screen (`#btnShop` etc.), screenshot it, and drive real DOM assertions (`$$eval` over rendered card/button text, `.classList.contains('maxed')`, `disabled` state) rather than just eyeballing a screenshot. Pre-seeding `localStorage['ruskoVoidSave']` via `page.addInitScript()` before `goto()` is the clean way to test specific upgrade-level/stardust combinations (fresh-save state, mixed-level state, all-maxed state) without having to grind a real run.

**For game logic/formulas (not visual, but numeric behavior), write a standalone Node harness and actually run it — this has caught real, non-obvious bugs, not just confirmed things looked fine:**
- `node --check` after every edit. `game.js` and `three.module.js` are real ES modules now — `node --check somefile.js` parses `.js` as a CommonJS script by default and will reject top-level `import`/`export` syntax as invalid; copy to a `.mjs` filename first (or use `--input-type=module`) to actually check ES module syntax. Don't let a false syntax-check pass (or fail) fool you here.
- A standalone Node.js harness that re-implements just the relevant formulas/constants from the shipped file and asserts on them, run against exact CFG constants. These live in the working directory during a session but are **not persisted** — rebuild as needed. Prior examples: `rift_harness.js` (debris-pause/no-backlog), `rift_ai_harness.js` (heart-movement/drone-FSM), `rift_ui_harness.js` (yaw-facing blend + hit-flash decay + HP-bar-width), `shop_debug_harness.js` (free-purchase logic), `dist_events_harness.js` (#25's event-scheduler refactor, proving it fires at byte-identical `G.dist` values to the old hardcoded version across a simulated run).
- **Concrete example of why this matters, not just process box-checking**: the Rift redesign's first pass set `riftPassSpeed` to 55 units/sec, which looked reasonable by inspection. A harness run using a toy sine-wave ship speed caught it timing out ~40% of the time; digging into *why* revealed a structural pursuit-math bug (pursuer speed ≤ target speed can never converge), not a tuning issue. Fixed by raising to 220 and rewriting the harness's ship-speed model to the real sustained-speedCap worst case. **Lesson**: when a harness models a moving target something else has to catch up to, always include a stress case at the game's actual worst-case sustained speed, not a toy value that happens to stay under the real cap.
- Read the actual file back and grep/python-slice to confirm structure after any edit that touches HTML (an `HTMLParser`-based tag-balance check was used repeatedly).

## Architecture notes worth knowing before changing things

**Distance-gated world events are a small registry now, not hand-copied if-blocks (see Feature History #25) — this is the concrete hook for adding new events.** `DIST_EVENTS` (near the top of `game.js`, right after `CFG`) is an array of `{key, firstAt, every, trigger}`. `G.nextEventDist[key]` tracks each event's own next-trigger distance independently; `resetDistEvents()` (called from `resetRun()`) initializes them all from `firstAt`; the scheduling loop in `updateSpawning()` walks the array every frame and calls `trigger()` + advances `every` for anything `G.dist` has reached. **To add a new distance-gated event** (the debris storm / stardust vein / Rift-escalation ideas discussed but not yet built): write its `triggerXEvent()` function wherever makes sense, then add one `{key:'x', firstAt:..., every:..., trigger:()=>triggerXEvent()}` entry to `DIST_EVENTS`. Nothing else needs to change — not `resetRun()`, not the scheduling loop, not the debug hooks. (The one exception: if a debug hotkey should be able to force-trigger the new event like the existing Backquote/Rift one does, it needs its own `G.nextEventDist['x'] = G.dist + CFG.xEvery;` line next to the existing one, same pattern.)

**The Shipyard (`UPGRADES`/`renderShop`/`upgradeCost`) is already reasonably data-driven for adding new upgrade *tiers*** — `UPGRADES` is a plain `{name, desc, max, baseCost, step, icon}` table (`icon` added in #27, a single emoji shown at the head of each card — pick something thematically distinct per stat, nothing else needs to change to add it to a new entry), `renderShop()` iterates it generically, `upgradeCost()` derives cost from it. Adding a new upgrade type is: one `UPGRADES` entry (name/desc/max/baseCost/step/icon), one default field in `Save.data.upgrades`, one line in `shipStats()` wiring its effect. What's *not* generic is `shipStats()` itself — each upgrade's actual gameplay effect is a hardcoded formula there, which is appropriate for 5 different effects and would be overengineering to abstract further at this scale. **`renderShop()`'s card markup (see #27) is also worth reusing as-is for any new upgrade type** — it already handles the maxed/not-maxed and DEBUG/real-cost branching generically; a 6th entry in `UPGRADES` needs no changes to `renderShop()` itself. Russ has said he wants "a more expansive Shipyard eventually" (categories, more upgrade types, possibly cosmetic items) — nothing's been built toward that yet beyond confirming the current table structure will comfortably absorb more entries; a genuinely different *kind* of shop item (not just another stat upgrade) would be a real design conversation, not a mechanical extension.

**Every 3D model loads via a real `THREE.GLTFLoader` now — the hand-rolled base64/custom-parser pipeline is gone entirely (as of #40).** That pipeline (`parseGLB`, `readGLBAccessor`, `extractMeshParts`, `meshBoundsFromPositions`, `buildGLBParts`/`instanceGLBGroup`, `buildTurretRig`/`instanceTurretGroup`, `findMuzzlePoints` — 12-byte GLB header, JSON chunk `0x4E4F534A`, BIN chunk `0x004E4942`, manual accessor/bufferView resolution, all predating and unrelated to the ES-modules migration) only ever supported **flat-color, texture-less, single-mesh, no-skinning/animation models** — fine for the original embedded kit-piece models, not fine for any of Russ's textured Tripo models. #37 gave the player ship its own `GLTFLoader` path rather than extend the parser to handle textures (UV wrangling, image decoding, sampler wrap modes — a real can of worms for a deliberately-minimal parser); #39 and #40 moved the Rift orbiters and the regular turrets the same way, at which point the old parser had zero remaining callers and was deleted outright rather than left as dead code (see #40) — a future model that genuinely only needs flat-color/texture-less loading again would need to pull the implementation back out of this project's git/session history, not assume it's still here.

**Models, each loaded once via `GLTFLoader` and shared across every pooled instance via `.clone()`:**
- **Player ship** (#37) — `assets/player_ship.glb`, a single instance, loaded via `buildShip()`. See Feature History #37 for the full migration and open first-pass items (`SHIP_SCALE` in particular).
- **Void Rift orbiter drones** (#39) — `assets/enemy_drone.glb`, **pooled**: the model loads once and every `riftDronePool` slot (5) is populated from that same loaded template via `.clone()` (shares geometry/material by reference — one GPU copy no matter how many orbiters exist). See Feature History #39 for the full migration and open first-pass items (`RIFT_DRONE_SCALE` in particular).
- **Regular roaming turrets** (#40) — `assets/turret.glb`, also **pooled** the same way (`dronePool`, 16 slots), same `.clone()`-per-slot pattern `riftDronePool` established. Visually a single-mesh "spherical droid with guns all over it" (Russ's words) — **not** the old rig's two-node base+independently-swiveling-head shape, so there's no separate head to aim anymore: the whole pool-slot group rotates to face the player instead (see `updateOneDrone()`), and firing goes through the same `fireEnemyBullet()` every other enemy uses (no more per-barrel muzzle-point offsets — `fireTurretBurst()`/`findMuzzlePoints()` are gone along with the parser they depended on). See Feature History #40 for the full migration and open first-pass items (`TURRET_SCALE` in particular).
- **Void heart** (#41) — `assets/void_heart.glb`, **per-encounter** rather than pooled: unlike the drones/turrets, there's only ever one heart alive at a time and it's created fresh each Rift, not drawn from a persistent pool. The model still loads exactly once at module-init time into a template (`voidHeartTemplate`), recentered the same `THREE.Box3().setFromObject()` way; `triggerRiftEvent()` then calls `.clone()` on that template each time a Rift starts, rather than pre-populating pool slots the way `dronePool`/`riftDronePool` do. A genuine (not dead-code) fallback to the old primitive `THREE.IcosahedronGeometry` mesh is deliberately kept for the narrow case where `triggerRiftEvent()` fires before the async GLTFLoader has resolved — see Feature History #41 and below.

The regular turrets and Rift orbiters still live in **two separate pools** (`dronePool` size 16, `riftDronePool` size 5) because they need different per-frame update/AI logic (stationary-and-aiming vs. orbiting-and-diving), even though both now share the same GLTFLoader-once/clone-per-slot loading shape. Any code touching "enemy drones" generally needs to handle both pools — see `updateDrones`/`updateOneDrone` and `bulletHitsDronePool`.

**The void heart is now `void_heart.glb` (#41), with the old primitive geometry kept as a real fallback, not dead code.** `voidHeartGeo`/`voidHeartMat` (the original `THREE.IcosahedronGeometry(2.6,1)` + emissive magenta `MeshStandardMaterial`, right above `clearRiftOrbiters()`) are still declared and still used — `triggerRiftEvent()` checks `useHeartModel = !!voidHeartTemplate` and falls back to `new THREE.Mesh(voidHeartGeo, voidHeartMat)` if the GLB hasn't finished loading yet by the first Rift trigger (extremely unlikely in practice — the model is small and starts loading at module-init, well before a player can reach the first Rift's spawn distance — but structurally reachable, unlike the fully-dead old GLB parser removed in #40). The hit-feedback pulse (scale swell + emissive glow, see #23) is preserved for both paths: `G.rift.heartMaterials` holds whichever material(s) are actually in play (the GLB's per-mesh materials, with emissive properties set at load time since the source model has no authored emissive channel, or the single placeholder material) and `G.rift.heartBaseScale` holds whichever base scale applies (`VOID_HEART_SCALE` or `1`), so `updateRift()`'s pulse math (`heart.scale.setScalar(G.rift.heartBaseScale * flashScale)`, `mat.emissiveIntensity = ...`) doesn't need to know or care which path spawned the heart. Collision radius vs. player bullets is still hardcoded separately (`2.6+0.5`) and was deliberately left untouched — see Known open items.

**Player-ship collision radius is a separate hardcoded fudge factor, NOT derived from the ship mesh/bounding box.** Every obstacle-vs-player collision check (`updateAsteroids()`, `updateOneDrone()`, and the equivalent bullet-hit check) uses the same pattern: `Math.abs(dz)<1.6 && Math.hypot(dx,dy) < o.data.r+0.9` — the `+0.9` is the player's own hit-radius contribution, a flat constant, completely independent of whatever `SHIP_SCALE`/model geometry the ship visually renders at. This was specifically checked during #37 (grepping for a `CFG.player`/`shipRadius`-style constant came up empty, which is what led to finding this inline `0.9`): choosing `SHIP_SCALE` by matching the new model's visual *width* to the old model's width (both #37's approach) keeps this collision feel intact automatically, since the fudge factor was originally tuned against the old ship's on-screen size, not its literal geometry. If `SHIP_SCALE` (or a future model swap) is ever chosen some other way and the ship starts looking noticeably bigger/smaller than its actual hitbox, this `0.9` constant (three call sites, currently unnamed/uncentralized) is the one to retune — worth promoting to a named `CFG` constant if it's ever touched.

**Embedded image assets, two different patterns depending on whether JS needs to pick between them:**
- **Static, single-use images** (the two main-menu logo images) are embedded directly as markup in `RuskosVoid.html`: `<img src="data:image/webp;base64,...">`. WebP, quality 90.
- **Images JS needs to switch between at runtime** (the 4 countdown graphics) are a JS constant in `game.js`, `COUNTDOWN_IMG_BASE64`, mapping key → data-URI string, reassigned onto a single `<img>`'s `.src`.

**Object pooling** (`makePool`/`getFree`) is standard for every *high-frequency* spawned entity type (asteroids, both drone pools, pickups, bullets, rings). For genuinely rare events (explosions), plain allocate-and-discard is fine.

**Procedural canvas textures, no external image assets** for anything that doesn't need to be photographic — `proceduralNebulaTexture()`, `proceduralPlanetTexture(hue)`, `proceduralFireballTexture()`, `proceduralBulletGlowTexture()` all draw onto an offscreen `<canvas>` and wrap the result in a `THREE.CanvasTexture`.

**First real audio sample assets (Feature #33) — a new pattern alongside everything above.** Every sound effect before this was pure oscillator/noise synthesis inside `Audio_` (`tone()`/`noise()`, see the AUDIO section near the top of `game.js`) — zero audio files anywhere in the project. Real recorded `.wav` files now live in a plain `audio/` folder that sits next to `game.js` on disk (`C:\Users\Russ B\JSgames\NullSector3\audio\`), referenced by a `SFX_URLS` map (`key → 'audio/whatever.wav'`), loaded once via `fetch()` + `AudioContext.decodeAudioData()` into `Audio_.buffers{}` (`loadSamples()`, kicked off from `Audio_.init()` — fire-and-forget, no blocking), and played back through a new generic `Audio_.playBuffer(key, gain)` (fresh `AudioBufferSourceNode` per call, same `this.master` output bus as every procedural sound). Deliberately **external files, not base64-embedded like the GLB models/logo images** — decoding happens once regardless of source format, so the only real tradeoff was file size, and base64-inlining ~1.9MB of `.wav` data would have bloated `game.js` by roughly a third for no benefit (unlike the GLBs, these aren't parsed/manipulated in code, just handed straight to the browser's own decoder). Any future real-sample SFX should follow this same shape: one `SFX_URLS` entry, decoded once into `Audio_.buffers`, played via `playBuffer()`.

**Rare one-off VFX (explosions) use a plain array, not a pool.** `explosions` holds `{sprite, mat, light, life, maxLife}`; `spawnExplosion()`/`updateExplosions()`/`clearExplosions()` are the three entry points.

**Debug/testing hooks are URL-gated, off by default.** `const DEBUG = new URLSearchParams(location.search).has('debug')` near the top of `game.js`. Everything dev-only lives inside `if(DEBUG){...}` in the `/* DEV / TESTING */` section near the bottom of the file (before the main loop) — currently the Backquote skip-to-Rift hotkey and the "DEBUG: FREE SHOP" button. Extend this section (or add sibling `if(DEBUG){...}` blocks) for future dev tooling rather than inventing a new mechanism.
