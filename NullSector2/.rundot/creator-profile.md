## Key decisions
- 2026-08-28 -- Stage 0 check: only dev-tested so far, no external playtesters yet (not himself replaying for fun, not his apprentice or friends). Noted honestly rather than assumed -- means the retention/monetization suggestions below are structural/design analysis, not validated against real player reaction yet. Recommended getting a couple of real playtesters before investing heavily in any of it.
- 2026-08-28 -- Retention/monetization analysis (asked directly, skipping ahead of Stage 2 FTUE -- fine, stages aren't a strict gate). Key finding from reading the code: every powerup/upgrade (fire rate, spread, max HP, speed, shield) resets every single run in `reset()` -- there is zero cross-run progression today, despite a comment in the code implying `baseSpeed` was meant to be a "permanent upgrade level." The only existing return-hook is score-chasing (local top-10 + the new global top-100 leaderboard) -- real, but historically only retains the competitive slice of players, not casual ones. Content is one fixed sector/one boss/4 identical hive nodes with per-run randomized positions -- structurally a true "one level" game, not just a description. No daily-return mechanic, no notifications, and zero monetization surface (no ads, no IAP) exist yet.
- 2026-08-27 -- Ported single-file `ruskos_descent.html` into a Vite + RUN SDK project (`JSgames/NullSector2/`), original file left untouched (still referenced by his GitHub Pages site). Migrated the local top-10 high-score table from `localStorage` to `RundotGameAPI.appStorage` -- localStorage isn't available inside the RUN.world game iframe at all.
- 2026-08-27 -- Local dev environment stood up: Node/npm were already present but PowerShell's execution policy was blocking `npm.ps1`; fixed with `Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned`. `npm run dev` now works.
- 2026-08-27 -- Next feature, in scope now: rework the local top-10 table into a real cross-player RUN.world leaderboard (`RundotGameAPI.leaderboard`) and show the signed-in player's avatar (`RundotGameAPI.getProfile().avatarUrl`) in-game. Checked with rundot-game-coach whether this needs an additional installed skill -- it doesn't; leaderboard/profile aren't in the coach's routed stage list (analytics/FTUE/retention/monetization/mobile-UX/marketing/multiplayer), they're direct SDK API usage already covered by `rundot-sdk` + the bundled `LEADERBOARD.md`/`PROFILE.md` docs.

- 2026-08-27 -- Instrumented Stage 1 telemetry (boot triad + a per-run core-loop funnel + a leaderboard-engagement funnel + run_completed/game_error custom events) and shipped the leaderboard + avatar rework: real cross-player leaderboard (scrollable top 100) additive alongside the existing local top-10 table, plus a profile avatar badge on the title/leaderboard screens. `rundot-analytics` skill isn't installed on the account, so this was built from the SDK's own bundled docs instead -- functionally equivalent, worth pointing him at installing that skill if he wants its specific conventions later.
- 2026-08-28 -- Shipped Stage 5 mobile UX: the canvas was fixed 640x640 with zero resize handling, so it would've clipped on any phone. Now VW/VH recompute from available screen space on resize/orientation-change (bounded 320-960px), giving a vertical shape on portrait phones and horizontal on landscape/desktop, with devicePixelRatio-aware crisping and `RundotGameAPI.system.getSafeArea()` for RUN.world host chrome (CSS `env(safe-area-inset-*)` covers OS notches as an instant fallback). Also found and fixed a real (not just cosmetic) gamepad bug: the game read raw `navigator.getGamepads()`, which isn't reliably available inside RUN.world's sandboxed iframe on Steam Deck / mobile hardware controllers -- migrated to `RundotGameAPI.gamepad`'s normalized model with the original raw-browser code kept as an automatic fallback (used whenever the SDK gamepad layer isn't supported, which is always true in local dev since the mock doesn't implement it). Verified headlessly at 5 viewport sizes plus live mid-game orientation flips and a full playthrough with simulated touch+keyboard+mouse simultaneously -- zero errors.
